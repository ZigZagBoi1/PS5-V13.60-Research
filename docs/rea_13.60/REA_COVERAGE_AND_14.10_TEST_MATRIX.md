# PS5 13.60 REA Coverage and 14.10 Candidate Test Matrix

**Date:** 2026-10-14  
**Purpose:** Record what the 13.60 live-memory dump actually supports, distinguish binary observations from inherited FreeBSD-source claims, and stage 14.10 validation.

## Answer to “did we REA all of 13.60?”

No. The first REA pass covered the syscall-table path around slots 220–222. This follow-up expanded Ghidra analysis to selected syscall, IPv6, ICMPv6, AIO, and event-flag windows. It is still a targeted review, not a whole-kernel bug census.

The input is a **partial live RAM reconstruction**, not a decrypted kernel executable: SHA-256 `c3f745e25dc25ee7afef89eb418b295b6334bbefe8aa17e6886483c35d78cddd`, with 13,369,344 bytes of captured text and 90,177,536 bytes of data. The data span has 688 unmapped pages represented by zeroes. A separate prologue scan reports 25,890 possible function starts, but those starts are heuristic and have not all been validated or decompiled.

## REA coverage completed

**Update 2026-10-14 (session 3, corrected after raw-record check):** selected Sony dynlib syscall identities were mapped by trampoline resolution (see `REA_DYNLIB_CLUSTER_FINDINGS.md`). Bounded reads of raw 13.60 sysent records show slots 589, 590, and 597 each have `narg=0` and point to the generic `nosys` handler at `0xffffffff9e655760`; their omission from `syscall_table_1360.txt` is consistent with that result, but the generator behavior was not independently verified. The text file claims 314 implemented entries out of 700, yet its rows 677–699 contain implausible `narg`/handler values, so the upper bound and total count are not validated. This does not show that syscall 590 is new in 14.x; its 14.10 handler remains unidentified, and the saved live result is only a game/RPC failure. The raw records also correct narg for 612/656/659 to 1/2/3. `get_info`/`get_info2` show bounds/size checks in the 13.60 dump; `get_obj_member` has a bounded selector and 8-byte copyout, but a sensitive kernel-data leak is not established without field provenance. No-crash race attempts do not prove Sony added locking.

**Prior coverage:** I built a compact PE carrier from byte-for-byte copied regions of the dump, hash-checking the source first. A synthetic entry stub adds direct static call references so Ghidra starts analysis at selected kernel functions; the stub is analysis scaffolding and is not part of the PS5 image. The REA carrier is `rea_import/ps5_1360_attack_surface_analysis.exe` (SHA-256 `08c090080366fd6877f72b4d0378f084e11a698ddef0819d7c8916aadf9dd67f`). Its reproducible builder is `build_rea_attack_surface_carrier.py`.

The carrier maps 14 selected regions: the syscall trampoline/common handler/table, IPv6 option processing and callers, ICMPv6 input/error-handling area and its nearby jump tables, AIO, and event-flag code. Ghidra 12.1.2 reports 44 procedures and two strings in that carrier. Eleven AIO/event-flag/IPv6 procedures and two ICMPv6 procedures were decompiled in the recorded REA pass. Decompiled output is evidence about those bytes, but names/types are mostly inferred and some functions have incomplete control-flow or calling-convention recovery. No exploitability conclusion follows from a function merely being present.

The prior syscall-table review remains applicable to the original 13.60 capture: table slots 220–222 route through a common error path that returns `0x4e` (FreeBSD `ENOSYS` 78) on the observed path. The generated `# semget` label is not proof of a working SysV semaphore syscall. This says nothing definitive about firmware 14.10.

## 14.10 test order

1. **Recover/verify the RPC execution state.** TCP health alone only proves a listener accepts connections. The last Lua request returned no output, so do not queue a second request until a print-only request completes end-to-end.
2. **Build an exact candidate-to-handler map.** Use verified 14.10 syscall numbers, return conventions, sandbox gates, and handler identity. Never infer 14.10 from the FreeBSD number table or 13.60’s syscall labels alone.
3. **Run benign reachability and cleanup checks, one request at a time.** Record the full source, UTC time, firmware identity, raw output, return halves/errno, cleanup result, and post-request health.
4. **Compare code before selecting a trigger.** A 13.60 function match only ranks a lead; it does not show that 14.10 retained the vulnerable instructions.
5. **Keep races and memory-corruption triggers as separate, candidate-specific tests.** Only consider one after its preconditions, a reliable concurrency harness, and a recovery plan are established. “Test every single one” cannot mean indiscriminately firing every hypothesis: several are duplicate patterns, false positives, unreachable paths, or tests that can reboot the console.

## Current conclusion

The expanded REA pass improves coverage of selected 13.60 networking, AIO, and event-flag code and confirms the earlier instruction-level finding that CVE-2020-7469’s stale-pointer pattern is patched in the 13.60 dump. Socket/API round-trip success was never evidence that the vulnerable parser was reached. No candidate in this report is confirmed as exploitable on 14.10. The next useful step is to finish the 13.60 candidate mapping and restore one-at-a-time, non-triggering RPC validation before ranking any risky test.
